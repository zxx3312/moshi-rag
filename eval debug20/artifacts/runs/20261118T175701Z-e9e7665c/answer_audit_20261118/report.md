## 5. 主要问题及定位

### P1：比较答案取反，核验只能阻止，尚不能纠正

0016–0018均取到George Schnéevoigt于1961年去世、Anthony Mann于1967年去世，却把u5填成Hotel Paradis。
原始judge和末尾复核都给出了该错误值。后续原模型核验明确指出应为Devil's Doorway，并拒绝释放错误事实。
控制器将u5降为UNRESOLVED，最终说无法确认，因此本次不是日期检索失败，也不是核验误拦正确答案。
逐字引用正确没有阻止数值比较错误；LoRA并不自动保证推理更好。

证据见 [0016日志](../samples/0016/events.jsonl) 和 [诊断摘录](diagnostics.jsonl)。
位置：`llm.py::JUDGE`、`grounding.py`、`controller.py`的事实拒绝及末尾复核路径。
后续可考虑把核验理由送回同快照内的有限判断修复，再重新验证；不能把核验解释未经验证直接当答案。

### P2：批量核验连带丢失正确事实

0046/0047中，LoRA正确判断William为电视编剧，却也把仅有film director/producer证据的Jon判为yes。
核验正确指出Jon没有电视编剧依据，但facts_rejected同时包含u1/u2，导致William正确事实一起降级。
这不是William证据缺失，而是整批事实处理的粒度问题。即使保留William，完整No仍涉及B的职业缺省否定口径；普通系统没有自动采用该规则。
后续可按明确的单元级拒绝结果处理，避免一条坏事实牵连另一条好事实；本次没有修改实现或放宽规则。

### P3：一次judge JSON失败直接终止

0048的failure为`LLM did not return one valid JSON object`。此前已说过William的yes，随后judge调用失败，系统输出通用失败说明。
此次没有生成可供结构修复的judge_reply，也没有judge_repair调用。无法从已保存日志确认具体坏JSON文本，不能猜测为截断、网络或内容错误。
可考虑在provider解析边界增加有限修复和安全诊断；不做无限重试。

### P4：拆题错误仍然绕不开

0049–0051把“二者中谁获奖”读成“两个人获奖时间之间的获奖者”。LoRA收到的已经是错误计划，无法靠判断训练还原整道题。
0010–0012仍有多余身份单元；0037–0039又缩成单纯昵称识别，没有独立覆盖共同创办关系。
应检查问题的答案类型与关系覆盖，而不是仅看计划结构是否合法。此次不修改提示词。

### P5：身份限定与属/种边界

0055计划subject为`Gordonia (genus)`，证据标题为`Gordonia (plant)`；原文明确说是植物属，仍被身份校验拒绝。
0056/0057计划subject是`Gordonia (plant)`，同一证据能够通过。这说明存在限定写法造成的过度拒绝风险，后续需要专门核对兼容类型，不能放开所有括号限定。
另一方面0057用`Osbeckia stellata`这个物种的科支持整个`Osbeckia`属，属于真正的关系层级问题，不能靠放松身份检查解决。

### P6：引文逐字正确，但支持集合不完整

0005只引用一方死亡日期，0042比较结论只引用一方参赛年份，0057使用物种句，0059/0060使用专辑旧名句。
这些引用都可以在原文找到，但不一定足以支持当前关系；本轮B共5条声明因引用/支持不足被拒绝。
这与“省略号不是连续原文”的格式错误不同，不能因逐字格式改善就认为证据判断已解决。

另外10条B严格值失败主要是：6 February 1961与February 6, 1961的3次日期写法、United States与American的6次口径，以及Fundy与Bay of Fundy的1次短值。
这些记录应与真实关系错误分开阅读，但原B评分保持不变。
